# Fixing a e2e-net-sdk bug

This repo's Go clients are generated by `oapi-codegen` from E2E's own OpenAPI
specs (`specs/e2e.openapi.json` for MyAccount, `specs/e2e-tir.openapi.json`
for TIR). E2E's specs have real, confirmed authoring bugs: wrong types
(`integer` declared where the live API returns a float), wrong formats
(`format: date` on a field that isn't RFC 3339), undeclared path parameters,
and at least one field whose real semantics don't match its declared type
at all (`ssh_keys` expecting key IDs where it actually wants the public key
text). See `scripts/patches/myaccount.json` and `scripts/patches/tir.json`
for the full, documented list already fixed this way.

**The fix never goes in `client.gen.go`.** That file is regenerated by
`scripts/generate.sh` and any hand-edit is silently discarded next time
someone runs it. The fix goes in the *spec*, via a patch entry, so it
survives regeneration and documents *why* the spec is wrong.

## Step 1 — confirm it's a spec bug, not a caller bug

Read the actual error. Common signatures of a spec bug:

- `json: cannot unmarshal number X.0 into Go struct field ... of type int` —
  the field is declared `integer` but the live API returns a float.
- `json: cannot unmarshal number into Go struct field ... of type string` (or
  the reverse) — declared type doesn't match the live type at all.
- `parsing time "..." as "2006-01-02": cannot parse "..." as "2006"` (or
  similar) — `format: date` / `format: date-time` doesn't match what's
  actually returned.
- `<field>: failed to pass regex validation` — a `format: email` (or similar
  constrained format) on a field that isn't actually that format; oapi-codegen
  generates a validating type for these.
- A `400`/`412` from the live API on a request the generated types happily
  built — the request shape itself is wrong (see `ssh_keys` in
  `scripts/patches/myaccount.json` for a worked example: the field expects
  raw public key text, not the numeric key ID that `GetSshKeys` returns).
- `unexpected response (status %d): %s` from your own calling code, where the
  body doesn't match any declared response variant — the response schema is
  incomplete or wrong for that status code.

If the error is instead a normal Go compile error, a wrong function/field
name, or a straightforward usage mistake in *your* code (not the SDK), this
skill doesn't apply — just fix your code.

## Step 2 — find the exact schema location

The two raw source specs are in `specs/`. The one actually used to generate
code is the *patched* version, `specs/e2e.openapi.fixed.json` (myaccount) or
`specs/e2e-tir.openapi.fixed.json` (tir) — built by
`scripts/fix_spec.py <raw> <patches> <fixed>` inside `scripts/generate.sh`.

Find the operation and field:

```bash
python3 -c "
import json
d = json.load(open('specs/e2e.openapi.json'))
op = d['paths']['/api/v1/YOUR/PATH/']['get']   # or post/put/patch/delete
print(json.dumps(op['responses']['200']['content']['application/json']['schema'], indent=1))
"
```

Walk the printed schema to the exact field. Note its declared `type` and any
`format`.

## Step 3 — reproduce and confirm live, if you can

If the crash came from a real API call, you already have your evidence — the
error message plus the value that broke it. Keep both; they go in the patch's
`bug` field.

If you're investigating cold, call the live endpoint directly (curl or the
`ec2.RequestEditorFn` pattern in `example/lifecycle/main.go`'s `withE2EAuth`)
and compare the actual JSON type/value against the schema. **Every request
to E2E's API needs three things together** — confirmed by reading E2E's own
`e2e-cli` source, not documented anywhere in their spec or docs:

```
Authorization: Bearer <E2E_AUTH_TOKEN>
User-Agent: cli-e2e
?apikey=<E2E_API_KEY>          (query param, alongside the header above)
```

Missing any one of the three gets a `403 API not public` from the gateway,
before your request ever reaches E2E's actual backend logic.

**If confirming requires creating a real resource (a node, a bucket, ...):**
create the smallest/cheapest one, capture the crash, and **delete it
immediately** — before you finish writing the patch, not after. Real
resources cost real money for as long as they exist. `scripts/find_bugs.py`
sweeps every safe, parameter-less GET endpoint for free (no resource
creation) and should be your first move — it does not need this step.

## Step 4 — write the patch entry

Add an entry to `scripts/patches/myaccount.json` or `scripts/patches/tir.json`
(matching whichever spec the endpoint belongs to). Every entry needs:

- `method`, `path` — exactly matching the spec's path template (with `{}`
  placeholders as written).
- `bug` — plain-English description: what's declared, what's actually
  returned/expected, and how you confirmed it (a specific value seen live,
  a resource id, a date — evidence, not "it seemed wrong").
- `fix` — one of the fix types `scripts/fix_spec.py` implements. Read that
  file for the current list and exact required fields per type; as of this
  writing:
  - `set_response_field_type` (+ `new_type`, `status`, `media_type`,
    `schema_path`) — wrong declared type on a response field.
  - `drop_response_field_format` (+ `status`, `media_type`, `schema_path`) —
    keep the type, drop a wrong/misleading `format`.
  - `reclassify_to_path` / `reclassify_to_query` (+ `param`) — a parameter
    declared in the wrong `in:` location.
  - `add_path_param` (+ `param`, `schema`) — a path template placeholder
    with no matching parameter declared at all.
  - `retype_schema` (+ `param`, `new_type`) / `retype_schema_by_index`
    (+ `param_index`, `new_type`) — wrong type on a request parameter.
  - `simplify_body_array_enum` (+ `param`, `new_schema`) — a request body
    shape (typically a `oneOf`) that breaks `oapi-codegen`'s Go generation;
    replace it with a simpler, equivalent schema.

  If none of these fit, you're adding a new fix type — implement it in
  `scripts/fix_spec.py` following the existing pattern (walk `schema_path`,
  apply one targeted change, nothing else) before using it in a patch entry.

`schema_path` is a list of alternating `"properties"`/key names (and bare
`"items"` for array element schemas) from the operation's response schema
root down to the field — see any existing entry for the exact shape, or
`scripts/find_bugs.py`'s `build_patch_entry()` for how it's constructed
programmatically.

## Step 5 — regenerate, build, verify

```bash
./scripts/generate.sh          # patches, splits, regenerates every module,
                                # then runs gofmt/build/vet on each — stops
                                # at the first failure
```

If it completes, every module still builds with your fix applied. Then:

```bash
make all                       # fmt-check, vet, lint, build across everything
```

If your fix affects `example/lifecycle`, rebuild and, if you can, re-run it:

```bash
cd example/lifecycle && go build ./... && go vet ./...
```

## Step 6 — commit

Conventional Commits, enforced by a local hook and CI
(`.github/workflows/commitlint.yml`):

```bash
make hooks   # once, if not already installed
git add scripts/patches/*.json specs/*.fixed.json myaccount/ tir/
git commit -m "fix(myaccount/<module>): <field> is declared <X> but returns <Y>

<one or two sentences: what broke, how you confirmed it, what changed>"
```

Don't hand-edit any `client.gen.go` or `openapi.json` inside `myaccount/*/`
or `tir/*/` — those are generator output. If your diff touches one of those
without a corresponding patch-file change producing it, something's wrong.
